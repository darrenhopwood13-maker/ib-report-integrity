Not a new feature: four defects in how a report behaves

Found in a read-through of the report workflow before launch, re-checked against the code. Two of them let the product make a promise it could not keep to a client. All four are fixed and live, plus the fifth change that stops an issued report moving under a client's feet.

1
A share link no longer serves an unpublished report.

Was: reopening a published report to correct one line put it back to in-review, and everyone already holding a link could read the working copy, with nothing on the page saying so. Now: nothing outside your organisation reads a report that is not published - one rule, in one place, every report.

2
Allocating a trade no longer counts as approving the wording.

Was: publishing is blocked until items are confirmed by a person, but both allocation paths were writing the confirmation stamp - so sending an item to a bricklayer satisfied that gate, and a report could go out asserting every item had been read when nobody had read it. Now: allocation writes only the trade and the date, and the record calls it allocation. Editing the wording, remedy, severity, grade, cause or location withdraws the approval, so it must be given again deliberately.

3
A client email for an unpublished report is refused, not sent empty.

Was: the send did not check status, so pre-issue it lost its share link and its PDF and went out anyway. Now: it refuses, and says what to do instead. An empty envelope to a client is worse than a refusal.

4
The close-out email link goes somewhere a supplier can open.

Was: it pointed at an in-app page needing a sign-in, which no subcontractor has; and a trade work pack for an unpublished report went out looking like the finished client report. Now: it uses the same no-sign-in token page the trade pack uses, says so when no such page exists rather than printing a dead link, and a work pack for an unpublished report is labelled DRAFT WORK PACK on the face of it and in the subject line.

5
A share link serves the version it was minted against.

Was: a link read the live report, so re-issuing could quietly change what an already-sent link showed. Now: it is pinned to the frozen version it was created from. Links created earlier carry no pin and keep resolving to the current version, so nothing already sent changes behaviour.

Live and verified, 12 October 2026. Published to instructbrain.com. Build clean, type checker clean, 917 automated tests pass, no lint errors. The share-link change was checked against the real data: 16 links exist, all 16 unpinned, none pointing at a missing version, none orphaned from its report.

What this does not claim. The fixed behaviours are covered by automated tests and the code is live, but each was not separately exercised end to end on a live report in front of a client - the confirmation gate, for instance, is tested rather than demonstrated by deliberately issuing an unconfirmed report. Existing share links are unaffected by design and were checked at the data level, not opened one by one.
